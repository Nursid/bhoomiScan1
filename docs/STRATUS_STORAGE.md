# Zoho Catalyst Stratus document storage

## Verification status

- **Implemented:** Authenticated REST upload/download, OAuth refresh-token handling, owner-scoped retrieval, byte-size and SHA-256 integrity checks, unique object references, and best-effort cleanup are implemented in the backend.
- **Unit tested:** Mocked tests cover OAuth refresh, bounded authorization retries, upload, download, invalid response/size handling, object-key cleanup, and cleanup failures. PDF and PNG round-trips exercise the real routes, hashing, and Stratus client with HTTP/Prisma mocked. Tests also cover cross-series duplicate rejection and safe handling of uncertain database insert outcomes. These tests do not contact Zoho or a database.
- **Live smoke-tested (Development bucket):** On 2026-10-16, a harmless temporary text object was uploaded and downloaded through the existing client; downloaded bytes and SHA-256 matched the source. Cleanup was scheduled for that exact generated key with a 60-second delay. A later read-only GET for that key returned HTTP 404, confirming the object was gone. The key was `verification-tests/a27824c7-33af-4ed6-9bd9-c751eaf0d7b4.txt`. This verifies the storage API path, OAuth access used by the test, and byte integrity for this small text sample; it is not an end-to-end PDF/image API, PostgreSQL, or blockchain test.
- **Cleanup correction:** The smoke check initially found the cleanup REST URL had an extra trailing slash after `/bucket/object`, which returned HTTP 404. The client now uses the documented endpoint path without that slash and reports HTTP status plus a sanitized provider message on failure. A fresh exact-key cleanup was accepted and its delayed deletion was confirmed with a later GET.
- **Bucket permissions:** Requests used OAuth authentication against the configured Development bucket. The bucket's console ACL was not independently inspected during the smoke test; keep it authenticated/private and do not infer public-access settings from the successful request.
- **Database blocked:** The storage-object-key migration is present but unapplied. Neon PostgreSQL is the provider; no local server is required. Wait for an isolated Neon `bhoomiscan_test` database, explicit process-environment `TEST_DATABASE_URL`, and approval for database access/migrations/destructive tests. Keep application `DATABASE_URL` unchanged; follow the README's safe Neon test instructions.

BhoomiScan uses the configured private Stratus bucket for original PDF/image bytes. The API computes SHA-256 from the uploaded bytes, stores the bytes in Stratus, and stores only document metadata, hash, and the unique Stratus object key in PostgreSQL. The object key is not exposed in API responses. Authenticated download first checks the BhoomiScan document owner and streams bytes through the backend; it does not return a permanent bucket URL.

Each document version receives its own random object key. Upload completes before the database record is created or blockchain registration is attempted. If upload fails, no document row or chain registration is created. If the database rejects the insert with a unique/foreign-key constraint error (`P2002`/`P2003`), the backend makes a best-effort cleanup request for that attempt's newly generated key. For other insert errors, a lost response may hide a committed row: the backend looks up that attempt's document ID and resumes registration if it finds the row. Otherwise it preserves the object and reports the original error. A missing row immediately after a timeout is not proof that the insert cannot still commit. Retained objects may require reconciliation after database availability is restored; no automatic orphan sweep is implemented. A later blockchain retry uses the stored object reference and does not re-upload the document. Version uploads cannot return duplicates from a different document series.

## REST API and region

The configured bucket URL uses the India Stratus data center and Development environment:

```text
https://bhoomiscan-documents-development.zohostratus.in/{object-key}
```

The implementation uses the Stratus object API directly:

- `PUT {STRATUS_BUCKET_URL}/{object-key}` with raw bytes, file `Content-Type`, and `Authorization: Zoho-oauthtoken {access_token}`.
- `GET {STRATUS_BUCKET_URL}/{object-key}` with the same authorization header; the backend streams the result only after an ownership check.
- Cleanup after a definite unique/foreign-key insert rejection uses the Catalyst India API `PUT https://api.catalyst.zoho.in/baas/v1/project/{STRATUS_PROJECT_ID}/bucket/object?bucket_name={STRATUS_BUCKET_NAME}` with a JSON `objects` entry for the unique key and `ttl_in_seconds: 60`, plus `Environment: Development`. The API schedules deletion after the TTL; acceptance is not proof that deletion has completed. For a smoke test, record the generated key before upload and verify only that exact key after the delay.

Object keys are generated by the backend, contain only safe path characters, and are unique per document version. No user supplied path or object URL is accepted. Downloads have a size check against the recorded file size and the 10 MiB upload limit. Successful file-download responses set `Cache-Control: private, no-store`.

## OAuth setup required

Create/register a Zoho OAuth client in the Zoho API Console for the same India-region Zoho account and authorize the Catalyst project with the least required scopes:

```text
Stratus.fileop.CREATE
Stratus.fileop.READ
ZohoCatalyst.buckets.objects.DELETE
```

The delete scope is used only for best-effort cleanup of a unique object after a definite unique/foreign-key insert rejection or an unsuccessful/ambiguous storage PUT before database insertion. An ambiguous database insert is handled by recovery or retention, not deletion. Cleanup targets the generated key only. The application does not delete normal document versions.

For initial authorization, request offline access and all three scopes through Zoho's OAuth flow, exchange the one-time authorization code at `https://accounts.zoho.in/oauth/v2/token`, and place the resulting refresh token and client credentials in the backend secret configuration. Access tokens expire after about one hour; the backend refreshes them with a POST to `https://accounts.zoho.in/oauth/v2/token` using `grant_type=refresh_token`, `refresh_token`, `client_id`, and `client_secret` as form parameters. Access tokens are cached only in process memory until shortly before expiry. They, refresh tokens, and client secrets are never stored in PostgreSQL or logged.

Configure these names in local development and the AppSail backend environment; put actual credentials only in the secret store/environment and never commit them:

```text
STRATUS_BUCKET_NAME
STRATUS_BUCKET_URL
STRATUS_PROJECT_ID
STRATUS_OAUTH_CLIENT_ID
STRATUS_OAUTH_CLIENT_SECRET
STRATUS_OAUTH_REFRESH_TOKEN
```

For this project, the values should identify the existing `bhoomiscan-documents` Development bucket, its console-provided `.zohostratus.in` URL, and Catalyst project `Project-Bhoomi`. `STRATUS_PROJECT_ID` is the numeric project ID used only by cleanup. The configured bucket must remain authenticated/private; no public or presigned permanent URL is returned.

The first pre-fix live upload attempt reported `STRATUS_CLEANUP_FAILED`; its generated key was not recorded, so that particular object was not included in the later exact-key deletion check. Do not infer that it was removed. The follow-up smoke test documented above used a newly generated, recorded key and confirmed its delayed cleanup. No other bucket object was targeted.

## API

`GET /api/v1/documents/{id}/file` returns the owned document's original bytes with an attachment content disposition. It requires the same BhoomiScan Bearer authentication as document history and does not accept a Stratus key from the caller.
